1. Entendimiento del problema

Qué resolvemos: un reemplazo que, tras POST /__reset, responda a secuencias de 1 a 12 requests con el mismo status y el mismo cuerpo que el original, errores, rutas inexistentes y autenticación incluidos. Además: una especificación en la que cada afirmación cite el log, y un log de experimentos con hipótesis. El éxito se mide con los 100 tests ocultos (solo 3 corridas) evaluados contra la versión vigente a las 20:00.

Lo que ya muestran los 20 ejemplos: un protocolo de texto CMD;arg…;control dentro de {"m": …}. Parece un mini core bancario (PING, ALTA, CONSULTA, DEPOSITO, TRANSFER, ANULA) con familias de error E2xx (integridad), E3xx (sintaxis), E4xx (inexistente) y E5xx (negocio), y con estado por token (contadores AC-000N y OP-000N).

Supuestos (a validar con el log):

  • S1 El último campo es un dígito de control calculado sobre el resto del mensaje (ALTA;Lucia;83 falla y ;82 pasa). Es la primera puerta: sin él, nada funciona.
  • S2 Los contadores AC/OP son por token y vuelven a 1 con el reset.
  • S3 ANULA revierte saldos: AC-0002 vuelve a 40000 y luego falla una transferencia de 50000.
  • S4 TRANSFER tiene un límite. 120000 falla y 100000 pasa: ¿es por operación o acumulado? Está por probar.
  • S5 El servicio cambia durante el día (hay un incidente anunciado a las 15:30).

Casos difíciles:

  • El orden de evaluación cuando un mensaje dispara varios errores (E201/E202/E301/E302/E401/E5xx).
  • La respuesta sin token, con token ajeno, con cuerpo vacío o no-JSON, y en rutas o métodos inexistentes.
  • Montos en 0, negativos, decimales o enormes. Transferencias a la misma cuenta. Anular algo inexistente.
  • Rarezas que hay que copiar literalmente: "recieved", cuentaId vs cuenta_id, el espacio final en "comando desconocido ", CONSULTa aceptado.

Fuera de alcance (y por qué): la persistencia entre reinicios, porque el set hace reset antes de cada test. Los headers, porque no se comparan (pero X-Req sí se registra en el log). El escalado horizontal, porque el set le habla a un solo proceso.

2. Arquitectura y trade-offs

Tres componentes. (A) El explorador (enviar.py + un fuzzer propio): consulta el original con el token personal y escribe cada request en experimentos.jsonl con su hipótesis. (B) El reemplazo: un servicio FastAPI organizado como pipeline Auth → Router → Parser → Integridad → Comandos → Estado → Formateador. (C) El replayer: corre las mismas secuencias contra el oráculo grabado y contra el clon, y compara con la misma regla del set. El clon nunca llama al original.

Riesgos principales: que no se descubra el dígito de control (es la prioridad #1, se ataca con fuzzing variando un carácter a la vez); que el cambio de las 15:30 rompa el clon (se mitiga con la regresión M4 y la tabla de errores como datos); el rate limit (throttle a 8 rps); que la plataforma levante varias instancias (réplicas fijadas en 1).
